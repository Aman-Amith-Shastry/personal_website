CampusAI

Hackathon · 2026

Overview

Planning a semester at Michigan means holding a degree audit, a course catalog, and a requirements page in three tabs and reconciling them yourself. CampusAI is my attempt to just ask the question instead.

It indexes the requirements for roughly sixty programs — Data Science in Engineering, Computer Science in LSA, and everything else advising publishes — alongside the general academic rules, then answers audit-style questions about what a student still owes and which of the courses that satisfy it are actually being offered. The interesting constraint was that requirement documents are prose, not a schema: "one of the following three sequences, unless you have credit for" is the normal shape of the text. Retrieval over the source documents beat trying to model any of that as a database in a weekend.

How it works

Corpus
A scraper (requests + BeautifulSoup) pulls each program's requirement document, converting the Google Docs links advising publishes into their plain text export before parsing, and writes one file per major. Academic rules and the program list are kept as CSVs alongside them.
Retrieval
Documents are embedded with a sentence-transformers model and stored in a Qdrant vector store, exposed to the model as a LangChain retriever tool — so lookup is a tool call the model decides to make, rather than a fixed block of context stuffed into every prompt.
Live course data
A second tool queries the University's Schedule of Classes API by term, school, and subject for the catalog numbers currently on offer. Requirements come from the indexed documents; what is actually schedulable this term comes from the API, so answers do not recommend a course nobody is teaching.
Serving
FastAPI and uvicorn behind a React frontend built with Vite.

It was built over a hackathon weekend and the repository still reads like it — the retrieval path went through two rewrites in about thirty hours, and the code that survived is the second one.

What I’d do differently

  • Converge faster on the idea. Most of day one went to ideating and getting the repository set up. Neither was wasted, but a weekend has about thirty usable hours in it and that was a large fraction of them spent before anything existed to iterate on.
  • Agree on the architecture before splitting up. We communicated, but not always about the right thing — people knew what they were building without always knowing what everyone else was. Settling the interfaces between the parts up front, or building the first version of each together, would have made integration a step rather than a scramble.
  • Timebox the search for data sources. A lot of the weekend went into finding APIs that would actually return what we needed. That search is real work and it happens on every project like this, so it is worth treating as its own task with a deadline instead of something to get through on the way to building.
